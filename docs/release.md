# Release process

How raptor-opencode cuts and publishes a version.

## Files

| File | Purpose |
|---|---|
| `cliff.toml` | git-cliff config: gitmoji + conventional commits, grouped by type, merge commits skipped, contributors section disabled (single-author project). |
| `CHANGELOG.md` | Generated by git-cliff. Never edit by hand. |
| `Makefile` | `release-notes` and `release` targets. |
| `.github/workflows/release.yml` | On a `v*` tag push: regenerate the notes and create the GitHub Release. |
| `pyproject.toml` / `raptor_opencode/__init__.py` | Both carry the version; `tests/test_version.py` keeps them in sync. |

## Version bump

1. Edit `version` in `pyproject.toml` and `__version__` in
   `raptor_opencode/__init__.py`.
2. Run `make release-notes` to regenerate `CHANGELOG.md`.
3. Commit with a gitmoji (`🔧 chore(release): vX.Y.Z`) and open a PR to
   `development`, then `development` to `main`.

`tests/test_version.py` fails if the two version strings diverge or if the
`raptor-opencode version` subcommand does not print the package version.

## Tagging

From an up-to-date `main` with a clean working tree:

```sh
make release VERSION=0.1.0
```

The target refuses a dirty tree, a malformed version and an existing tag, then
creates an annotated tag `v0.1.0` (`🚀 release: v0.1.0`) and pushes it. The tag
push triggers `.github/workflows/release.yml`, which installs git-cliff 2.14.2,
generates the notes for that tag (`--latest --strip header`) and runs
`gh release create --latest` using the workflow `GITHUB_TOKEN` (no extra
secrets). `permissions: contents: write` is the only requirement.

## Notes

- `CHANGELOG.md` is reproducible: git-cliff output depends only on the commit
  history and the tags, so regenerating it twice yields an identical file.
- `make release-notes` before the tag exists labels the section `Unreleased`;
  run it again after tagging (or let the workflow do it) to get the dated
  section.
